# RCA eval results

Generated by `python evals/run_eval.py`. Six seeded incidents with known root
causes, scored against ground truth.

**Read the methodology caveat first.** These scores measure whether an RCA
mentioned the concepts a correct answer needs and avoided the wrong answer each
fixture was built to bait. That is a proxy for quality, not a measure of it.
The full list of what is not measured is in
[docs/06-evals.md](../docs/06-evals.md).

## Environment

| | |
| --- | --- |
| Hardware | Apple M3, 8 cores, 16 GB |
| Runtime | Ollama in Docker Desktop on macOS |
| Acceleration | **None.** Docker Desktop does not pass Metal through, so inference is CPU-only |
| Fixtures | 6 |

Latency figures here are therefore pessimistic against any deployment with GPU
access, and should not be compared to hosted-API numbers.

## Two scores, and why

| Column | What it measures |
| --- | --- |
| **in text** | Required concepts appearing anywhere in the RCA, including the explanation |
| **concluded** | Required concepts appearing in the `root_cause` field |

The split exists because the first version of this harness scored only full
text, and the **deterministic fallback scored 92% on it**. That looked like a
result until it was read: the fallback quotes raw log lines verbatim in its
explanation, so the keywords are present because the evidence was copied, not
because anything was concluded. Its actual `root_cause` field says
`"<service> shows repeated anomalous behavior"`.

A metric the null baseline can max out is not measuring what it claims to.
Splitting conclusion from evidence fixed it, and the gap between the two
columns is now the interesting number.

## What the failures have in common

This is the most useful thing in this document. Reading the actual outputs:

| fixture | model's root_cause | verdict |
| --- | --- | --- |
| memory-leak | "Heap usage exceeds the maximum allowed size, leading to a `java.lang.OutOfMemoryError`" | correct |
| disk-full | "disk space exhaustion" | correct |
| cert-expiry | "Certificate expiration and TLS handshake failure" | correct |
| db-pool-exhaustion | "Timeouts and connection issues in the orders service" | symptom, not cause |
| downstream-5xx | "5xx errors in the checkout service" | symptom, **and wrong service** |
| noisy-deploy | "Correlated anomalies in the catalog-service service" | pure restatement |

The three passes are the three fixtures where **the root cause is literally
named in a log line**: `OutOfMemoryError`, `No space left on device`,
`certificate has expired`. The three failures are the three where the cause has
to be *inferred from a relationship between lines*: pool stats explaining the
timeouts, an inventory 503 explaining a checkout failure, a SIGTERM plus a
version change meaning a deploy.

On this evidence the 1.5B model is doing entity extraction, not causal
reasoning. That is a reasonable thing for a 1.5B model to be doing, and it
matters for how the output should be presented: an RCA that confidently
restates the loudest error is more misleading than no RCA, which is why every
result carries its evidence.

`downstream-5xx` is the worst failure. It named the reporting service as the
cause when the fault was in its dependency, which is the specific mistake the
2 AM scenario in [docs/00-problem.md](../docs/00-problem.md) describes humans
making.

## Confidence is not calibrated

| | |
| --- | --- |
| Mean stated confidence, 1.5B | **0.92** |
| Actual pass rate | **3/6** |

Confidence never dropped below 0.90 on any fixture, including all three
failures. One failure was stated at 1.00.

AIRS already blends model self-assessment with a structural heuristic rather
than trusting it directly, which is the right instinct. This measures how
necessary that hedge is: on this evidence the model's own confidence carries
close to zero signal about correctness, so the blend is dampening noise rather
than combining two estimates.

**Do not present `confidence` to an operator as a probability.** It is not one.

## Reproducing

```bash
python evals/run_eval.py                                    # deterministic only
python evals/run_eval.py --llm --model qwen2.5:1.5b-instruct
python evals/run_eval.py --llm --model qwen2.5:7b-instruct
```

An earlier 7B run recorded here was discarded rather than published: the Ollama
container was stopped part-way through, so four of six fixtures fell through to
the deterministic path at 0.0 s and the aggregate looked like a reasoning
failure rather than an infrastructure one. The two fixtures that did complete
both passed at 100% conclusion recall, including `db-pool-exhaustion` which the
1.5B model failed, so the tier comparison is genuinely open rather than
resolved.

**Six fixtures is far too small a sample to rank two models.** Any tier
comparison from this harness should be read as a smoke test, not a benchmark.
