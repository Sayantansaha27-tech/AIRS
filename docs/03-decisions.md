# 03: Decisions

Architecture decision records. Each states what was chosen, what was rejected,
and what it costs. The rejected options matter more than the chosen ones,
because they are where the reasoning is.

---

## ADR-001: Kafka between stages, not HTTP

**Status:** accepted

### Context

Six stages need to hand work to each other. The AI stage is orders of
magnitude slower than the ingest stage, and its latency is unpredictable
because it depends on model inference.

### Rejected: direct HTTP between services

Simplest to build and to debug. Rejected on backpressure. With HTTP, a slow
ai-service applies backpressure through correlation and anomaly detection all
the way to the ingest endpoint. The stage least able to keep up would
determine the throughput of the stage most able to, and a model timeout would
surface as a failed log ingestion. That inverts the property this system most
needs: **incidents must exist whether or not the model does.**

### Rejected: RabbitMQ or SQS

A real queue solves backpressure. Rejected on replay. When an incident
pipeline produces a wrong answer, the question is always "what did it see?",
and answering it means replaying the exact input. Queues consume destructively.
Rebuilding state after a detection logic change means replaying days of
history, which a log-retention topic gives you and a queue does not.

Fan-out matters too. `processed-logs-topic` has one consumer today. Adding a
second consumer of the same stream should not require the producer to know.

### Chosen: Kafka

Durable ordered streams, independent consumer groups per stage, replay by
offset, fan-out without producer changes, and the dead-letter pattern falls
out naturally.

### Cost, paid knowingly

Kafka is the heaviest thing in the stack, and for a laptop-scale demonstration
that is a real cost. It is also operationally unfamiliar to many reviewers,
who will reasonably ask why a system processing tens of events per second
needs a distributed log. The honest answer is that the ordering and replay
properties are load-bearing for the diagnosis workflow, not the throughput.

Delivery was at-most-once for a while, because consumers used auto-commit and
a crash mid-batch lost in-flight events. That is fixed: consumers commit after
a batch is handled, giving at-least-once, and correlation deduplicates replays
against a durable key. Exactly-once would need a transaction spanning Kafka and
OpenSearch and is not built.

## ADR-002: A deterministic RCA fallback exists at all

**Status:** accepted

### Context

RCA is generated by an LLM. LLMs time out, return prose where JSON was asked
for, get rate limited, have their API keys expire, and are simply not running
on the machine you deployed to.

### Rejected: fail the incident when the model fails

Clean, and it never produces a low-quality answer. Rejected because it makes
model availability a hard dependency of incident response. The 2 AM scenario
in [00-problem.md](00-problem.md) is strictly worse if the tool that was
supposed to help is down for the same reason everything else is.

### Rejected: retry until it succeeds

Unbounded retry converts a model outage into an unbounded queue. The incidents
that most need attention are the ones generated during the outage.

### Rejected: leave `rca` null and let the UI show nothing

Tempting, and it is honest. Rejected because a null field forces every consumer
downstream, the UI, webhooks, ChatOps and any future ticket integration, to
handle two shapes. Populating the contract always is worth more than the
marginal honesty of a null.

### Chosen: cascade to a deterministic template

Primary model with retries, then the low-cost model with retries, then a
template over the incident context. The template names the service, counts
anomalies, quotes the top log lines and suggests generic remediation, with
confidence derived heuristically from signal volume.

Crucially it also covers **provider construction failure**, not just call
failure, so a misconfigured provider degrades rather than dead-letters.

### Cost, paid knowingly

The fallback is not an analysis and must never be presented as one. It is a
structurally valid RCA that tells you very little. Two mitigations:

- `airs_rca_success_total{path="deterministic"}` separates it from a generated
  RCA, so degraded operation is visible in Grafana rather than looking like
  health.
- Its own explanation text says it is a fallback.

The other cost is latency. A model that is unreachable rather than fast-failing
burns the full retry budget on both tiers, roughly 54 seconds, before falling
through. The RCA consumer is sequential, so lag grows for the duration of an
outage. Bounded and visible, but real.

## ADR-003: Severity-based model routing

**Status:** accepted

### Context

A 7B model on consumer hardware takes seconds per RCA. Most incidents are not
critical.

### Rejected: one model for everything

Either the good model on everything, which makes low-value incidents expensive
and starves the queue during a storm, or the small model on everything, which
degrades the incidents that matter most.

### Rejected: route on a cost budget

More principled, and it needs cost accounting, budget state and a policy for
what happens at exhaustion. Too much machinery for the value.

### Chosen: route on the severity already computed upstream

`critical` to the primary model, `warning` to the low-cost model, `info` to the
deterministic path with no model call. Severity is already computed by anomaly
detection and re-derived at correlation, so routing costs nothing to compute.

### Cost, paid knowingly

Severity is derived from log level, z-score and keyword markers, so a genuinely
serious incident that presents as `warning` gets the weaker model. Routing is
only as good as the severity classification feeding it. `force_model` in the
context, and `POST /v1/incidents/{id}/rca/regenerate`, are the escape hatches.

Note also that the low-cost tier only applies while the active provider is the
one it was configured for. `settings.llm.fallback_model` names an Ollama model,
and asking OpenAI for it produces a 404 and a wasted retry budget. After a
runtime provider switch, `warning` follows the active model and the meaningful
tier that survives is the deterministic one.

## ADR-004: OpenSearch, not Postgres or Elasticsearch

**Status:** accepted

### Context

Storage for logs and incidents, with full-text search over messages, time-range
queries, and aggregation for baselines and back-testing.

### Rejected: PostgreSQL

Excellent for incidents, which are structured. Poor for the log volume and the
full-text access pattern. `ILIKE '%connection refused%'` over millions of rows
is not a query, it is a wait. Rule back-testing against stored history is a
full-text scan by nature, and that is what tips it.

### Rejected: Elasticsearch

Functionally the better-known choice. Rejected on licensing. The SSPL change
makes it awkward to recommend for self-hosting without qualification, and this
project's whole posture is "run it yourself".

### Chosen: OpenSearch

Apache-2.0, self-hostable, API-compatible with Elasticsearch so migration in
either direction is realistic, with ISM for retention built in.

### Cost, paid knowingly

Memory. OpenSearch is most of the 8 GB floor in the quickstart. It is also
eventually consistent by default, which is why writes that must be immediately
readable use `refresh=True`, and that in turn is a throughput problem measured
in [06-evals.md](06-evals.md). ISM is a plugin, so retention is best-effort:
`ensure_retention_policy` swallows failure so the service still starts on a
minimal OpenSearch.

## ADR-005: Correlation state in memory

**Status:** accepted, partially superseded

### Context

Correlation needs to know which anomalies are already grouped, over a window of
minutes.

### Rejected: OpenSearch as correlation state

Query open incidents per anomaly, append, write back. Correct, durable, and it
adds two round trips to the hottest path in the pipeline, with read-modify-write
races between them.

### Rejected: Redis

The natural answer, and Redis is already in the stack. Deferred rather than
rejected on principle: it is the migration path when this constraint starts to
hurt.

### Chosen: an in-process dict, with clusters resident for their window

Zero latency, no coordination. Windows are minutes, so the exposure is bounded.

### Cost, paid knowingly

This is the sharpest constraint in the system and it is worth stating without
hedging:

- **correlation-service does not scale horizontally.** Two replicas partition
  the anomaly stream and each sees half of a service's signals, so both may
  open an incident for the same event.
- **A crash loses open clusters.** Graceful shutdown flushes them; `SIGKILL`
  does not.
- The same applies to anomaly-service baselines, which additionally take an
  hour of wall-clock per hour-of-day slot to relearn.

The trigger for moving state to Redis was needing a second replica of either
service. It arrived earlier than that and for a different reason: moving Kafka
off auto-commit required a durable idempotency key, and there was nowhere
durable to put one.

So deduplication keys are in Redis now, and the pieces still in memory are open
correlation clusters and anomaly baselines. Two replicas still split those, so
this ADR is half-retired rather than reversed. The remaining work is mechanical
and the reason to do it is unchanged.

## ADR-006: Validate at the produce boundary

**Status:** accepted

### Context

Six services exchange five message types. Contract drift between independently
deployed services is the classic microservice failure.

### Rejected: a schema registry service (Confluent-style, Avro)

The industrial answer. Rejected as disproportionate: another service to run,
another failure mode, and code generation in the build for five message types
that change rarely.

### Rejected: validate on consume only

Cheaper, and it detects drift too late. A malformed event is already on the
topic and every consumer has to handle it independently.

### Chosen: one shared Pydantic model set, validated on produce

`kafka.produce_json` validates the payload against the model registered for
that topic before publishing. A service cannot put a malformed event on a topic
even by accident, so consumers deserialize without defensive parsing. The
mapping is served over `GET /v1/schema-registry`.

### Cost, paid knowingly

All services must deploy the shared library in a compatible version, which is a
coupling. For a single-repo, single-deployment system that is a fair trade for
guaranteed contract integrity. Versions are declared but there is no
negotiation: a v2 would need a parallel topic or a version field in the
envelope. Not needed yet, so not built.

## ADR-007: Source and sink seams for outbound integrations

**Status:** accepted, and now implemented. See
[10-servicenow.md](10-servicenow.md).

### Context

The next block of work integrates ServiceNow: pull incidents from a ServiceNow
instance, run RCA over them, and write the result back as a work note.

That request breaks two assumptions baked into the current shape. First, that
input is always a *log* arriving on `logs-topic`, when a ServiceNow incident is
already an incident. Second, that RCA output goes to OpenSearch, when a work
note is an outbound write to a third-party API with its own auth, rate limits
and idempotency requirements.

### Rejected: build the ServiceNow integration now

Speculative. The interface would be shaped by one implementation, which is how
you get an abstraction that fits exactly one case.

### Rejected: do nothing and refactor when it lands

The likely outcome is ServiceNow specifics leaking into ai-service and
correlation-service, because that is the path of least resistance under time
pressure.

### Chosen: define the two seams now, implement neither

- A **source** interface that log ingestion and a future ServiceNow poller both
  satisfy, so a new input is a new source rather than a new pipeline.
- A **sink** interface for RCA output, so storage, a webhook and a ticket work
  note are three implementations of one contract.
- Outbound calls isolated behind an adapter carrying retry, backoff and
  idempotency keys, because writing a work note twice is a visible defect in
  someone else's system.

No ServiceNow-specific assumption enters core services. The constraint the
seam is designed against, stated so it can be checked: **ai-service must not
know that ServiceNow exists.**

### Cost, paid knowingly

Two interfaces exist with fewer implementations than justify them today, which
is a real smell. Accepted because the driver is named, dated and specific
rather than hypothetical. If the ServiceNow work does not happen, these should
be deleted rather than left as evidence of a plan.

### What the seams turned out to require

The integration landed shortly after, and two things about it were not obvious
when this ADR was written.

**Outbound delivery could not live in ai-service.** The intuitive design is a
sink registry that ai-service consults after generating an RCA. That satisfies
the letter of "no ServiceNow-specific assumption in core services" while
missing the point, because the ServiceNow module ends up imported into
ai-service's process either way.

Instead ai-service publishes the enriched incident to `enriched-incidents-topic`
and connector-service consumes it. ai-service does not import the sink seam at
all. This also buys the isolation every other stage boundary buys: a
hibernating ticketing system cannot slow RCA generation.

**The `Incident` contract needed a provenance field.** `SourceRecord` and
`SinkPayload` both carried `external_id`, but the only thing travelling between
a source and a sink is the `Incident`, which had nowhere to put it. The ticket
id was lost mid-pipeline and the sink had nothing to address. Adding optional
`source_system` and `external_id` closed it.

That is the general shape of the lesson: a seam at each end is not enough if
the thing passing between them cannot carry what the seams agreed on.
